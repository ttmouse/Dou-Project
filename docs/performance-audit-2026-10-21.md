## 已复现并修复

### 1. 数据快照构造与复制隐式执行 Git

`Project.init` 不论是否已经提供完整元数据，都读取文件属性并调用 `loadGitInfo`。后者可能启动两个 Git 进程。标签复制、Git 历史回写和 ProjectData 转换都通过这个初始化器，导致后台采集完毕后仍可能在主线程执行 Git。

回归夹具：临时创建只有一次提交的真实仓库，50 次构造完整快照，每次再复制标签和 Git 历史。修复前 Debug 耗时 **20,376.53 ms**；修复后 Debug 为 **0.19–0.35 ms**，Release 为 **0.15 ms**。这是这条特定路径的耗时，不代表整个应用的加速比例。

修复：仅在元数据缺失时读取磁盘。Git 提交数参数用 nil 表达“未提供”，显式 0 保持为 0。两个 copyWith 均保留 activityAt。未提供元数据的首次发现路径仍能获取 Git 信息，有单独测试。

### 2. 排序与日期筛选读取上一次状态

Combine 的 @Published 在属性赋值前发送事件。原同步 sink 忽略传入值，转而读实例属性，因此读取旧的 sortOption/dateFilter。回归测试证明，单次切换排序或日期时结果慢一次操作。

修复：这两类同步订阅切到下一轮主队列，跳过初始值并去重，随后读取已写入的完整状态。结果数组相同时不再发布 filteredProjects，避免无用的视图刷新。

增加 ProjectListSource 注入接口，以真实排序器和内存来源验证整个 ViewModel，无需创建会读写真实用户数据的 TagManager。

### 3. 大 Git 历史可能堵塞管道

原实现先 waitUntilExit，再读取 stdout。子进程输出超过管道容量时等待父进程读取，父进程则等待子进程结束。用 262,144 字节子进程输出复现同一等待顺序的阻塞，排空输出后进程正常退出。

修复：先持续读取 stdout，再等待进程结束；不消费的 stderr 接 nullDevice，并检查退出码。HEAD 查询复用同一执行函数。12,000 次提交的真实 Git 夹具验证完整历史采集及字段保留。

单项目历史刷新也统一调用 copyWith(gitDaily:)，避免旧的手工重建漏掉 activityAt、startupCommand 和 customPort。

### 4. 隐藏标签的状态来源与无用计算

过滤读取 appState.filter.hiddenTags，而原订阅监听另一个 hiddenTags 属性。改为监听实际使用的状态来源，并在监视目录变化时更新列表。

没有隐藏标签时跳过整轮过滤；有隐藏标签时只计算一次所选隐藏标签集合，逐项目使用 isDisjoint，避免每个项目都创建交集。

## 后续重构顺序

1. **收敛双份项目状态。** Project 与 ProjectData 同时存在，后者不含 activityAt，转换还会读取项目备注；这是数据一致性和主线程 I/O 的后续审计重点。先补转换契约测试，再决定唯一状态模型，避免直接大规模迁移。
2. **合并文件事件的状态发布。** 批量更新逐项修改 @Published 字典，可能产生重复通知和数组复制。需要用真实事件风暴测量后再决定批次快照的边界。
3. **记录真实交互帧时间。** 用 Instruments 区分输入、滚动、目录事件、Git 更新时主线程的占用，按最大阻塞排序，而不是按文件大小排序。
4. **完善异步保存的生命周期。** 原注册测试已有临时目录删除后定时保存报错；本次同样观察到，测试断言通过并不表示这条生命周期没有缺陷。
5. **单独审计分支操作的进程执行器。** ShellExecutor 仍有先等待进程结束再读双管道的同类模式；它同时承载修改分支的命令，需要保留错误输出语义后再配套验证。本轮修改限于项目列表及只读 Git 历史采集。

原则：先减少每次交互必做的工作，再考虑并发与缓存；只有证据证明现有界面技术限制性能时才考虑整体重写。

## 续审：Git 回填对列表响应的影响

同日继续检查，发现 Git 虽已在后台采集，完成后的逐项发布和排序依然制造大量主线程工作。

已执行：

- 历史回填在内存中合并，整批只发布一次 projects；相同数据不发布。
- git_daily 不影响排序键，直接替换排序缓存中的原位置，不逐项删除后重新插入。
- 列表订阅独立的历史变化事件，替换已有数据，不重新搜索、过滤或建立搜索索引；不可见项目变化不重复发布可见列表。
- 不重建标签索引，不触发与 Git 历史无关的 Finder 标签同步；缓存仍走后台原子写入和合并防抖。
- 普通注册、两个全量更新入口和新项目后台采集共用串行采集及回填链路。主线程先取快照，后台不再直接读取可变项目字典。
- 只把历史合并到当前仍存在的项目，保留用户在采集期间修改的其他字段，不把已删除的项目重新添加回来。

回归夹具为 3,000 个已有项目，每项回填同样的历史字符串。把旧的逐项发布/排序循环接入测试入口后，测试因 3,000 次发布与标签缓存失效而失败，耗时 **1,611 ms（Debug）**。新批量路径初测 **12.7 ms（Debug）**，最终 **5.19 ms（Release）**，发布次数为 **1**。这些测量包含合并、排序缓存替换及保存任务安排，**不包含 SwiftUI 绘制，也不包含 Git 采集**，不能视为完整帧时间。

新增三个测试覆盖批量发布与顺序保持、保留实时编辑及忽略已删项目、列表不因历史变化重新筛选或排序。全量 **87 个测试、1 跳过、0 失败**；Release 下两个相关测试类的 **16 个测试全部通过**。

证据及独立测试应用位于 artifacts/git-backfill-20261021。应用通过 codesign --verify --deep --strict 校验。原有测试临时目录清理后仍有延迟保存报错，未把测试通过解释为保存生命周期已修复。

边界：当前仍有一次必要的主线程状态提交及可见视图更新。尚未做 Instruments 的真实滚动帧时间采样，不承诺任何机器、任意项目规模和资源压力下绝对无卡顿。
